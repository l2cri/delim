# 06: Жадное сведение

**What to build:** Операция ядра «сведение» с жадным алгоритмом: балансы → список
переводов «кто→кому сколько» (максимальный должник гасится максимальным кредитором).
Контракт: не более n−1 переводов, точные минорные суммы, детерминированность, нулевые
балансы не участвуют (ADR 0006, 0010). Это первый слой алгоритмического обещания приложения.

**Blocked by:** 05 (балансы как вход седения)

**Status:** done

- [x] Классический пример из питча сводится к ожидаемым двум переводам
- [x] Края: 0 и 1 участник (пустой результат), все в нуле, несвязные группы гасятся внутри себя без лишних переводов между группами
- [x] Копеечные остатки: ни один перевод не нулевой и не отрицательный
- [x] Сумма переводов погашает все балансы точно; результат стабилен при повторных вызовах
- [x] Тесты проверяют контракт (число переводов, погашение), а не порядок обхода

## Замечания ревью

Двухосевое ревью (Standards — AGENTS/ARCHITECTURE/GLOSSARY/WORKFLOW, Spec — тикет,
SPEC, ADR 0006/0010) против merge-base с master. Блокирующих P1/P2 нет. Исправленное
в ветке по P3: комментарии тестов о границах жадного — несвязные группы с точными
парами гасятся внутри, нулевые подмножества без точных совпадений жадный может
пересечь лишним переводом (это ограничение жадного слоя отдано точному solver-у
тикету 07, ADR 0006); невозможность ненулевого баланса у единственного участника;
доказуемые минимумы длин (3 = n−1 без нулевых подмножеств, 3 = (2−1)+(3−1) для двух
компонент) — чтобы ассерты выжили при подключении точного solver-а.

Отложенное (P3/P4, мерж не блокирует):

- Фикстуры участников и расхода повторяют balances.test.ts буквально — при третьем
  повторе (тикет 08) вынести в общий тестовый хелпер.
- Тест питча сверяет точные объекты переводов toEqual — решение там единственно
  минимально, порядок списка не проверяется; на неоднозначных входах так нельзя.
- Имена `Working`/`rest` в settle.ts чуть универсальны; семантика закомментирована.
