# Workflow: git worktree + сессия на тикет

Стратегия параллельной разработки: каждая тикет-сессия ZCode работает в отдельном
git worktree со своей веткой; готовый тикет мержится в master с видимым merge-коммитом.
Роли и зоны агентов — в [AGENTS.md](AGENTS.md), порядок тикетов — в [tickets/README.md](../tickets/README.md).

## Принципы

1. **Сессия = тикет = worktree = ветка.** Одна сессия закрывает один тикет и умирает.
   Никаких долгоживущих сессий «на весь проект».
2. **Параллелизм ограничен фронтом, а не числом рук.** Ветка тикета создаётся только
   после того, как все его блокаторы смержены в master (правило фронта из tickets/README).
   Максимальный реальный параллелизм этого DAG — 3 ветки, чаще 2. Больше worktree —
   не быстрее, а конфликтнее.
3. **Конфликты подавлены архитектурой.** Зоны агентов (core / state / ui) почти не
   пересекаются по файлам; всё, что пересекается, уже разведено по блокирующим рёбрам.
4. **История видна.** Мержи — только `--no-ff` (через PR «Create a merge commit»),
   каждый коммит несёт номер тикета. Сквош запрещён: он съедает историю сессии.

## Роли

| Роль | Кто | Что делает |
|---|---|---|
| Штаб | сессия ZCode в главном чекауте `delim/` (проект «Делим пополам») | смотрит фронт, создаёт worktree под тикет, делает/принимает мержи, ревьюит ADR-комплаенс |
| Тикет-сессия | сессия ZCode, открытая в папке worktree | главный агент сессии = владелец тикета по AGENTS.md; порождает субагентов, ведёт тикет до done |
| Субагенты | algo-core / app-state / ui-craft / qa-acceptance | работают внутри тикет-сессии по своим чартерам |
| Вы | человек | создаёте сессии, жмёте кнопку мержа PR, смотрите `git log --graph` |

`.zcode/agents/` закоммичен в репозитории → каждый worktree содержит определения
субагентов, сессия в worktree их видит.

## Жизненный цикл тикета

```bash
# 0) Штаб: убедиться, что блокаторы тикета NN в master, затем
git worktree add ../delim-trees/t09 -b t/09-expenses     # слог ветки — латиницей

# 1) Открыть новую сессию ZCode в C:\Users\l2cri\Projects\delim-trees\t09
#    Промпт первого сообщения: «Работай по тикету tickets/09-расходы-сплиты.md,
#    ты — первичный владелец по docs/AGENTS.md, статус в in-progress»

# 2) Тикет-сессия: работа по чартеру, коммиты малыми шагами:
#    #09 core: красная фаза — тесты сведения
#    #09 ui: форма расхода, три режима сплита
#    #09 test: края — нецелое деление поровну
#    Чекбоксы тикета отмечаются по ходу; тесты — до зелёного.

# 3) Финал тикет-сессии:
git push -u origin t/09-expenses
#    + PR в GitHub: заголовок «#09: расходы — три режима сплита».
#    Status: done в файле тикета — последним коммитом ветки.

# 4) Мерж (вы или штаб): подтянуть master в ветку, убедиться что CI зелёный,
#    смержить PR кнопкой «Create a merge commit» (--no-ff). Сквош не жать.

# 5) Штаб, после мержа:
git worktree remove ../delim-trees/t09
git branch -d t/09-expenses          # ветку на GitHub удалит кнопка PR
git pull
```

## Конвенции

- **Ветки**: `t/NN-slog-latincej` (например `t/05-grossbuh`). Никакой кириллицы в именах
  веток и папок worktree — пути Windows вас поблагодарят.
- **Worktree**: `../delim-trees/tNN` — соседняя с `delim` папка, вне репозитория.
- **Коммиты**: `#NN <зона>: <что сделано>` — номер тикета обязателен, зона —
  core/state/ui/test/docs. Мелкие шаги приветствуются (красная фаза/зелёная фаза —
  отдельные коммиты): так в истории видно, как сессия думала.
- **Мерж-коммит**: создаётся GitHub-кнопкой; в заголовке PR уже стоит `#NN`.
- **Master**: всегда зелёный; CI гоняет vitest на каждый PR и пуш (настроен в тикете 01).

## Правила параллельности

1. Прежде чем создать worktree — проверь в tickets/README, что блокаторы тикета
   имеют Status: done **и** смержены (ветка садится на свежий master).
2. Держите ≤ 3 активных worktree. Фронт DAG всё равно не даст больше полезной работы.
3. Перед мержем ветка обязана подтянуть свежий master и пройти тесты на результате
   (`git merge master` в ветке → vitest → push). Конфликт — сигнал, что рёбра DAG
   нарушены: разберитесь, а не «разрулите руками» молча.
4. Локальные мержи в master без PR допустимы (например, нет сети), но тем же `--no-ff`
   и только из штаба — тикет-сессия master не трогает, у неё нет его чекаута.

## Bootstrap (разово, до тикета 01)

- [ ] `git init` в `delim/`, `.gitignore` (node_modules, dist, coverage)
- [ ] Первый коммит: `#00 docs: спека, ADR, архитектура, глоссарий, тикеты, команда`
- [ ] GitHub-репозиторий (имя — рабочий вопрос: `delim`), пуш master
- [ ] CI (GitHub Actions: npm ci + vitest) — это и есть тикет 01, но простой workflow-файл
      можно положить уже в bootstrap, чтобы история тикетов рождалась под защитой CI

## Известные трения (и почему это ок)

- Два параллельных тикета правят `tickets/README.md` (статусы) → тривиальные конфликты
  строк; решаются за секунды, приемлемо.
- Тикет-сессия не видит файлы блокатора, если он ещё не смержен → это не баг, а правило
  фронта: не начинайте тикет раньше времени.
- Worktree и главный чекаут делят один `.git` → фоновых сюрпризов нет, но одновременный
  `git gc`/rebase в двух папках не запускайте.
