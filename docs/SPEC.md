# SPEC: «Делим» v1 — offline-first сплиттер общих расходов

Статус: ready-for-agent. Источник: интервью grill-me (октябрь 2026), сводка подтверждена заказчиком.

## Problem Statement

После совместных выходных или путешествий компания вынуждена сводить дебет с кредитом
вручную: кто платил за такси, кто за бар, а кто не пил, но ел. Существующие приложения
(Splitwise и аналоги) перегружены и требуют регистрации от каждого участника. В итоге
расчёты либо не делаются, либо превращаются в переписку из скриншотов.

## Solution

Веб-PWA «Делим»: организатор за пару минут раскидывает чеки по компании — поровну,
точными суммами или долями, в любых валютах с ручными курсами — и получает минимальный
список переводов («А переводит Б 1500 ₽, В переводит Б 800 ₽») и наглядный граф долгов.
Участники открывают ссылку-приглашение как зрители, без регистрации и установки.
Приложение полностью офлайновое: данные в localStorage, шеринг — ссылка со сжатым стейтом
поездки. Никаких серверов и сетевых запросов.

## User Stories

1. As a организатор, I want создать поездку с названием и базовой валютой, so that начать сводить общие расходы.
2. As a организатор, I want добавить участников по именам, so that раскидывать расходы между конкретными людьми.
3. As a организатор, I want чтобы каждому участнику автоматически подбирался цвет и эмодзи, so that различать людей в списках и графе без ручной настройки.
4. As a организатор, I want перегенерировать цвет и эмодзи участника из палитры, so that поправить неудачный автоподбор.
5. As a организатор, I want переименовать участника в любой момент, so that исправить опечатку.
6. As a организатор, I want удалить участника, который не фигурирует ни в одном расходе и выплате, so that держать список чистым.
7. As a организатор, I want получить понятный отказ при попытке удалить участника из расхода или выплаты, so that не сломать историю молча.
8. As a организатор, I want добавить валюту поездки из пресета популярных, so that не вводить код вручную.
9. As a организатор, I want добавить произвольную валюту вручную, so that сводить расходы в экзотических странах.
10. As a организатор, I want задать курс каждой валюты к базовой вручную, so that приложение работало полностью без сети.
11. As a организатор, I want изменить курс в любой момент, so that вся поездка пересчиталась по новому курсу задним числом.
12. As a организатор, I want добавить расход — название, плательщик, сумма, валюта, сплит, so that зафиксировать общую трату.
13. As a организатор, I want ввести сумму выражением вроде «1500/4+200» и сразу видеть результат, so that считать не выходя из поля ввода.
14. As a организатор, I want раскидать расход поровну между выбранными участниками, so that разделить общий счёт одним действием.
15. As a организатор, I want назначить точные суммы отдельным участникам, so that учесть «кто не пил, но ел».
16. As a организатор, I want задать доли вида 2/1/1, so that делить неравные порции одним действием.
17. As a организатор, I want видеть предупреждение, пока сплиты не покрывают сумму расхода, so that не сохранить «дырявый» расход.
18. As a организатор, I want отредактировать или удалить любой расход, so that исправить ошибку ввода.
19. As a организатор, I want видеть список расходов с плательщиком, суммой и её эквивалентом в базовой валюте, so that понимать структуру трат.
20. As a организатор, I want видеть баланс каждого участника — кто сколько должен и кому должны ему, so that понимать картину долгов без вычислений.
21. As a организатор, I want зарегистрировать выплату «кто→кому сколько», so that зафиксировать возврат денег.
22. As a организатор, I want чтобы после каждой выплаты итоговые переводы пересчитывались мгновенно, so that список всегда отражал реальность.
23. As a организатор, I want видеть минимальный список переводов («А переводит Б 1500 ₽»), so that отправить его в чат одним сообщением.
24. As a организатор, I want видеть визуальный граф долгов, so that раскладка была наглядной без чтения цифр.
25. As a организатор, I want чтобы погашение долга анимированно убирало рёбра с графа, so that момент расчёта ощущался завершением.
26. As a организатор, I want сгенерировать текстовую квитанцию-сводку и скопировать её в буфер, so that отправить итоги в мессенджер.
27. As a организатор, I want получить ссылку, в которой лежит весь стейт поездки, so that поделиться без сервера и регистраций.
28. As a организатор, I want предупреждение, если ссылка выходит за практический предел длины мессенджеров, so that понимать ограничения до отправки.
29. As a зритель, I want открыть ссылку поездки с телефона и увидеть расходы, балансы и переводы, so that узнать свою долю без установки приложения.
30. As a зритель, I want сразу видеть, что поездка доступна только для чтения, so that не искать кнопки редактирования.
31. As a зритель, I want внятную ошибку вместо пустого экрана, если ссылка повреждена или создана другой версией приложения, so that понять, что попросить организатора новую ссылку.
32. As a организатор, I want установить приложение на домашний экран (PWA), so that открывать его одним тапом.
33. As a организатор, I want полную работоспособность офлайн — включая добавление расходов и выплат, so that сводить траты в роуминге и в горах без сети.
34. As a организатор, I want чтобы данные сохранялись автоматически после каждого изменения, so что не думать про «сохранить».
35. As a организатор, I want завершить поездку, so that зафиксировать финальные расклады.
36. As a организатор, I want открыть архивную поездку в режиме чтения, so that вспомнить прошлые расчёты.
37. As a организатор, I want начать новую поездку с пониманием, что архив предыдущей заменится, so что не копить старьё.
38. As a организатор, I want тёмную или светлую тему по системной настройке устройства, so that приложение выглядело родным.
39. As a разработчик, I want чтобы жадное сведение давало не более n−1 переводов, а точный поиск не хуже жадного, so that алгоритмическому обещанию приложения можно было доверять.
40. As a разработчик, I want целочисленную денежную арифметику без потери копеек, so that балансы сходились в ноль математически.
41. As a разработчик, I want строгую валидацию импортируемого стейта с версией схемы и лимитами, so that битые ссылки не роняли приложение.
42. As a организатор, I want интерфейс на русском языке, so that не переключать контекст с компанией.

## Implementation Decisions

Все решения ниже зафиксированы интервью и подтверждены заказчиком; ключевые также лежат
в [adr/](adr/). Термины — по [GLOSSARY.md](../GLOSSARY.md).

**Роли и жизненный цикл**
- Редактирует только организатор; зрители открывают ссылку в режиме только чтения (ADR 0001). Кнопки «продолжить локально» / форк у зрителя нет.
- Одна активная поездка; завершённая хранится в архиве глубиной 1, только чтение, затирается стартом следующей (ADR 0002).

**Структура данных**
- Стейт поездки — один сериализуемый объект: название, базовая валюта, список валют с курсами, участники, расходы, выплаты, статус (активна/архив), версия схемы. Именно этот объект хранится, кодируется в ссылку и валидируется при импорте.
- Участник: имя, автоназначенные цвет и эмодзи (перезапускаются выбором из палитры). Переименование свободное; удаление запрещено, пока участник фигурирует в расходах или выплатах — с понятным отказом. Лимит 20 участников.
- Расход: название (свободный текст), плательщик, сумма + валюта, сплит, авто-дата добавления. Режимы сплита: поровну между выбранными, точные суммы, доли. Сохранение блокируется, пока сплиты не покрывают сумму расхода.
- Выплата: кто, кому, сумма + валюта поездки. Лимиты поездки: 20 участников, 300 расходов, 200 выплат, 10 валют.

**Деньги**
- Внутри — только целые минорные единицы (ADR 0004). Курсы — точные рациональные числа (целая пара числитель/знаменатель), вводимые десятичной дробью.
- Курс — живое значение в настройках, расход хранит лишь сумму и валюту; правка курса пересчитывает всю поездку задним числом (ADR 0005).
- Конвертация долей — методом наибольших остатков, чтобы конвертированные доли в сумме точно равнялись конвертированному расходу.
- Итоговые переводы — точные суммы до минорной единицы, без «удобного округления».

**Сведение (минимальные переводы)**
- Гибрид: жадный алгоритм (максимальный должник → максимальный кредитор) всегда; при ≤ 12 участниках — дополнительно точный bitset-поиск, берётся лучший результат (ADR 0006). Детерминирован.
- Закрытие долга — только регистрацией выплаты «кто→кому сколько», включая частичные; сведение всегда производная от расходов и выплат (ADR 0010).

**Шеринг и валидация**
- Ссылка `#/t=…` несёт весь стейт, сжатый lz-string (ADR 0007). Генерация предупреждает о превышении практической длины (~32 000 символов), но не блокирует; импорт отвергает полезную нагрузку длиннее 100 000 символов.
- Импорт all-or-nothing: zod-валидация схемы, проверка версии (несовпадение → экран «ссылка от другой версии»), лимиты, референциальная целостность. Любой провал — экран «ссылка повреждена», без частичного импорта.

**Клиент**
- Vite + Vue 3 + TypeScript, PWA через vite-plugin-pwa (precache оболочки; после первого открытия работает офлайн). Вёрстка — Tailwind, без UI-кита.
- Стейт — композабл над сериализуемым объектом поездки, без Pinia (ADR 0009). Хранение — localStorage, автосохранение с дебаунсом ~500 мс (ADR 0008).
- Навигация — хэш: `#/` активная поездка/создание, `#/archive` архив, `#/t=…` зритель. Роутинг — собственный композабл, без vue-router.
- Калькулятор: обычный инпут + парсер выражений `+ - * / ( )`, запятая и точка равнозначны, живой предпросмотр результата, некорректное выражение подсвечивается молча.
- Граф долгов: чистый SVG, круговая раскладка с сортировкой по балансу, переводы — дуги с суммами; анимации на Vue-переходах, без d3-force.
- Квитанция — только текст, копируется в буфер. PNG не рендерим.
- Тема — авто по `prefers-color-scheme`, без ручного переключателя. Язык — только русский.
- Деплой — GitHub Pages (хэш-роутинг не требует SPA-редиректов).

## Testing Decisions

Хороший тест проверяет внешнее поведение через интерфейс ядра: контракты (число переводов,
сохранение баланса, погашение долгов), а не внутренности (порядок обхода, структуру
промежуточных данных). Тестов, которые «знают» реализацию, не пишем — иначе рефакторинг
алгоритма ломает тесты без изменения поведения.

Тестируемое ядро — чистый модуль без Vue (ADR 0003), он же главный шов: тесты, композаблы
и зрительский экран пересекают одну и ту же границу. Поверхность тестирования — пять
операций интерфейса ядра (схема, балансы, сведение, кодек, калькулятор — см.
[ARCHITECTURE.md](ARCHITECTURE.md)).

Три слоя тестов седения (Vitest):
1. **Краевые случаи списком**: ноль и один участник, все нулевые балансы, копеечные
   остатки, несвязные компоненты графа, компания ровно на пороге 12/13 участников.
2. **Property-based (fast-check)**: сумма балансов равна нулю; жадный даёт ≤ n−1
   переводов; точный результат не хуже жадного; конвертация сохраняет сумму расхода;
   кодек roundtrip; парсер выражений согласуется с вычислением «в лоб».
3. **Exhaustive-сверка**: для n ≤ 6 полный перебор эталонного минимума против обоих
   алгоритмов на всех балансовых профилях из небольшого пространства сумм.

Prior art отсутствует (greenfield) — тесты ядра станут образцом для остальных.

Vue-оболочка — только дымовые тесты ключевых экранов (создание, расход, зритель);
E2E-инфраструктура в v1 не входит.

## Out of Scope

- Регистрация и аккаунты любых видов; коллаборативное редактирование; сервер (Supabase и др.) в v1.
- API курсов валют, любые сетевые запросы.
- Рекуррентные расходы; банковские интеграции; push-уведомления.
- Мультиязычность (только русский); ручной переключатель темы.
- Проценты и разбор чека по позициям (блюдам).
- PNG-квитанция; Web Share API с файлом.
- d3-force граф; vue-router; Pinia; UI-кит; IndexedDB.
- Список поездок глубиной больше одной; форк поездки зрителем.
- «Удобное» округление переводов до 10/50/100 ₽.
- E2E-тесты.

## Further Notes

- Осознанные отступления от исходного питча (подтверждены заказчиком): localStorage вместо
  IndexedDB; ручные курсы вместо API; текстовая квитанция вместо PNG; нет форка зрителем;
  нет списка поездок. Каждое закрыто ADR.
- «Делим» — рабочее название; финальное имя и домен выбрать до деплоя.
- Базовая валюта выбирается при создании поездки из пресета (~10 популярных: RUB, USD,
  EUR, GBP, KZT, TRY, AED, THB, GEL, CNY) с возможностью ручного добавления.
- Организатор свободно редактирует и удаляет расходы и выплаты; единственный «выход» из
  поездки — завершение с архивацией.
